# 企业高管背调（Executive Diligence）

对目标高管及其关联企业做系统化背调：**基础信息 → 全网检索 → 社交监控（可选）→ 事件脉络 → 报告与台账**。全程只用公开信息，事实/指控/传闻分级标注，同名他人明确区分，每条结论带信源。

> 路径约定：本文档内的相对路径（如 `scripts/login.py`）以 skill 根目录（即 `skill/`，含 `SKILL.md` 与 `scripts/`）为基准解析；部署位置可任意，勿将 `.env`、Cookie 等敏感文件提交到仓库。

## 执行前：确认任务单（与用户对齐）

| 字段 | 说明 |
| --- | --- |
| 姓名 | 目标高管全名（+别名/曾用名/拼音） |
| 关联企业 | 曾任职/现任企业（含曾用名） |
| 同名区分线索 | 地域/年龄段/行业/职务，用于排除同名他人 |
| 输出位置 | 建议 `reports/<姓名>_<日期>/`（本机报告目录）下 |

### 背调模式选择（开始时与用户确认）

| 模式 | 包含内容 | 需要登录获取 Cookie？ |
| --- | --- | --- |
| 快速 | web 检索 + 摘要报告 | 否 |
| 标准（默认） | + 负面台账 Excel（`build_ledger.py`） | 否 |
| 深度 | + 社交监控（微博/小红书/公众号检索）+ 事件脉络 | 是（可选）——用 `scripts/login.py` 登录各平台获取 Cookie，或跳过社交监控 |

- 可选叠加：**deep-research 拓展**（并行深度检索，耗时显著增加，默认不启用）。
- 用户未明确选择时默认「标准」；涉 IPO、多企业、缠诉、舆情密集等场景建议「深度」并叠加 deep-research，最终由用户决定。

先做同名区分预判：目标是否与常见同名者（如企业高管、被公示的失信/涉诉同名者）混淆——沿用「B 不建议投诉」的处理逻辑，报告与台账中单独说明。

## 阶段 1：个人与企业基础信息

用 `web_search` + `web_fetch`（若已开启）检索并交叉验证：

1. **工商登记**：企查查/天眼查/爱企查/启信宝等页面的企业信息——法定代表人、股东、注册资本、成立/注销时间、历史变更（法人/股权/名称）
2. **任职履历**：现任与历史职务（董事长/法人/董事/高管），任职时间与公司
3. **股权结构**：直接/间接持股，对外投资，关联公司
4. **同名区分验证**：用「姓名+公司」限定检索；涉法记录按公司/职务/地域/出生年交叉核对，确认是否同一人

产出：任职表（企业-职务-起止-信源）、企业关联清单。

## 阶段 2：全网检索

按以下维度组合关键词检索，命中即记录（含 URL、发布时间、信源可信度）：

1. **新闻报道**：正面（成就/公益/任职报道）、中性（行业活动）、负面（争议/投诉/举报）
2. **司法与信用**：「姓名+起诉/被执行/失信/限高/股权冻结/行政处罚/裁判文书」；重点平台：中国裁判文书网、天眼查/企查查失信被执行记录、地方信用公示
3. **负面关键词**：姓名+（造假/行贿/受贿/欠薪/跑路/诈骗/内幕/违规/处罚/举报/丑闻）
4. **公司与行业**：企业名+（诉讼/纠纷/处罚/停产/破产/仲裁）

记录规范：每条 = 平台/账号、标题/内容、链接、时间、内容定性、主要侵权/违规点、来源可信度。负面内容按「L1 攻击性 / L2 失实传闻 / L3 客观事实」预判分级，但与台账入库时仍需人工复核。

### 阶段 2 拓展（可选）：deep-research 并行深度检索

**仅在用户选择启用 deep-research 拓展时执行本小节**（见执行前）；未启用则按上面的标准检索流程。启用时加载 `deep-research` skill，按其方法论把本阶段升级为**并行多路深度检索**：

1. **拆解子问题**（背调场景示例）：个人背景履历 / 任职与关联企业 / 司法信用 / 负面舆情 / 行业监管 / 同名区分 —— 每路一个后台子代理
2. **并行检索**：用 `subagent` 同时启动各路，每路子代理独立做多轮 `web_search`/`web_fetch`（或本地抓取兜底），提炼「事实 + 信源 URL + 时间」返回
3. **证据表**：汇总各路结果为证据表（结论 | 信源 | 日期 | 质量级 A/B/C），落盘到输出目录 `<姓名>_<日期>/research/`
4. **迭代补缺**：识别信息缺口与矛盾点，生成追问查询再补一轮
5. **综合**：把证据表并入阶段 4（事件脉络）与阶段 5（报告/台账）使用

适用判断：常规背调默认「标准」模式即可；涉 IPO、多企业、缠诉、舆情密集等场景可建议用户启用 deep-research，由用户确认后执行。

## 阶段 3：社交监控（可选，仅深度模式或用户要求持续监控时）

复用已部署的监控工具（一次性背调可跳过）。部署目录示例为 `D:\weibo-monitor` 等，实际以本机为准：

| 工具 | 位置 | 用途 |
| --- | --- | --- |
| 微博监控 | `<部署目录>\weibo-monitor` | 监控指定微博账号（改 `.env` 的 `WEIBO_UID` 为目标账号 uid） |
| 小红书监控 | `<部署目录>\xhs-monitor` | 监控指定小红书用户主页（`XHS_MODE=user` + `XHS_USER_ID`；**搜索模式不可用**） |
| 小红书评论 | `<部署目录>\xhs-monitor\comments.py` | 监控指定笔记的评论（`XHS_COMMENT_SHARE_LINK` 填分享短链） |
| 公众号检索 | `scripts/sogou_search.py` | 搜狗微信搜索公众号文章/主页（`--keyword` 必填、`--type` 2文章/1公众号、`--pages` 翻页、`--output` 输出 JSON；**仅公众号内容，不含视频号**） |

**登录态接入（Cookie）**：
- **方式 A（推荐，小白友好）**：`scripts/login.py` 交互选择平台，自动调用 `get_cookies.py` 扫码登录并写入对应 `.env`：
  ```powershell
  python scripts/login.py                          # 交互选择平台
  python scripts/login.py --platform xhs           # 直接指定平台
  python scripts/login.py --list                   # 列出平台与输出路径
  python scripts/login.py --env-dir D:\            # 输出到 D:\weibo-monitor\.env 等既有位置（或设环境变量 DILIGENCE_ENV_DIR）
  ```
  底层 `get_cookies.py` 也支持直用（平台：weibo / xhs / douyin / zhihu / channels / mp / wxweb）：
  ```powershell
  python scripts/get_cookies.py weibo --output <部署目录>\weibo-monitor\.env
  ```
  - ⚠️ **微信网页版（wxweb）账号限制**：部分微信号被腾讯安全策略禁止使用网页版微信（扫码后返回「暂不支持使用网页版微信」），此时无法进入视频号/搜一搜。另外，**视频号公共内容没有网页检索渠道**：视频号助手（channels）是创作者管理后台、无公开搜索，视频号内容的关键词检索只能在微信 App/桌面客户端内进行；网页端可用的替代是搜狗微信搜索 `https://weixin.sogou.com/weixin?type=2&query=<关键词>`——**仅索引微信公众号内容**（页面标注「以下内容来自微信公众平台」；实测 type=2 文章可用、其它 type 均空、无视频号结果），**不包含微信视频号**，检索视频号需在微信客户端内手动进行。
  - 在**无交互终端（自动化/CI）**里运行时，`input()` 会立即收到 EOF：脚本不会误抓，会自动降级为「等待关键 Cookie 或信号文件」。建议配合信号文件精确控制抓取时机（先删除旧信号文件再运行）：
    ```powershell
    Remove-Item D:\flag.txt -ErrorAction SilentlyContinue
    python scripts/get_cookies.py xhs --output <部署目录>\xhs-monitor\.env --signal D:\flag.txt --timeout-minutes 15
    # 用户扫码登录完成后：Set-Content D:\flag.txt go
    ```
  - ⚠️ 注意：小红书未登录也会下发匿名 `web_session`、知乎未登录也会下发匿名 `z_c0`，关键 Cookie 自动检测可能提前触发——需要等真正登录时请用 `--signal`。
- **方式 B（手动）**：浏览器登录后 F12 → Network → 复制 Cookie 头，粘贴到 `.env` 的 `WEIBO_COOKIE` / `XHS_COOKIE`。

> 登录由用户本人在浏览器完成，凭据不经过脚本；Cookie 等同登录态，仅存本机 `.env`，勿外传；失效后重跑 `get_cookies.py` 更新。

抓取结果先落地为 JSON（`_posts.json` 一类），作为台账与报告的数据源。

## 阶段 4：事件脉络

汇总阶段 1-3 的信息，按时间线梳理：

- 时间线格式：**时间 | 事件 | 信源 | 影响/关联**
- 每条标注信息级别：**事实**（官方/权威信源）、**指控**（单方/自媒体）、**传闻**（无法溯源）
- 识别矛盾点与存疑信息（如：官方公告 vs 自媒体指控的冲突；同名不同人的混淆）

## 阶段 5：报告与台账产出

1. **台账**：把负面条目整理成 JSON，用 `scripts/build_ledger.py` 生成/追加 Excel 台账（沿用 15 列格式：序号/分组/平台账号/标题内容/链接/发布时间/内容定性/主要侵权违规点/建议处置方式/处置优先级/预期成功率/处置状态/责任人/处置日期/备注）
   ```powershell
   python scripts/build_ledger.py entries.json "<输出目录>\<姓名>_负面内容台账_<日期>.xlsx"
   # 追加到已有台账：
   python scripts/build_ledger.py entries.json <已有台账.xlsx> --append
   ```
2. **报告**：按 `templates/report.md` 模板填充，输出 `<姓名>_背调报告_<日期>.md`
3. 可选：报告摘要推送到飞书（复用监控工具目录下 `lib/feishu.mjs` 的推送逻辑）

## 产出规范（硬性）

- **事实 / 指控 / 传闻三级标注**，负面内容仅作线索，不作结论
- 每条结论带**信源 URL 与检索日期**；无法核实的明确标注
- **同名他人明确区分**（公司/职务/地域/出生年交叉验证）
- 仅使用公开渠道信息；不侵入、不逆向、不伪造；不主动挖掘非公开个人信息（详见 `docs/compliance.md`）
- 报告含**风险评级**（高/中/低 + 依据列表）
- 交付物：背调报告（Markdown）+ 负面台账（Excel）→ 存到输出目录并告知用户

## 合规与免责

背调涉及个人信息与声誉，使用时必须遵守 `docs/compliance.md` 的边界：仅限公开信息、仅限合法用途、Cookie 仅存本机、风险自负。本项目按 Apache-2.0 开源，使用/再分发/商业化前请阅读 `LICENSE` 与 `docs/compliance.md`。
